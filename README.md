# Twoliter

A build tool for creating custom [Bottlerocket] variants.
See the [design doc] describing how Twoliter works.
We welcome ideas and requirements in the form of issues and comments!

[Bottlerocket]: https://github.com/bottlerocket-os/bottlerocket
[design doc]: docs/design/README.md

## Verifying an AMI

`twoliter verify ami --ami-id ami-0123456789abcdef0 --region us-west-2` checks that an AMI can be
reproduced from source:

1. It reads the variant, architecture, version and commit from the AMI's name (or its root
   snapshot's description). AMIs built from a dirty tree are rejected.
2. It clones the source (`--repo`, or an existing clean clone via `--source-dir`) and checks out that
   commit. Only variants with the `erofs-root-partition` image feature are supported; variants with
   an ext4 root filesystem are rejected before building.
3. It runs `cargo make` in the checkout, so the image is rebuilt with the twoliter version pinned
   there. Releases pinning a twoliter older than 0.26.0 are not expected to reproduce. The build
   output is written to `build.log` in the work directory, and its last lines are shown if the
   build fails; `--verbose` shows it as it runs instead.
4. In parallel, it downloads the AMI's root and data snapshots with coldsnap. Snapshots owned by
   another account, such as public Bottlerocket AMIs, are first copied into the caller's account;
   the copies are deleted afterwards, also when the download fails or is interrupted. If the build
   or the download fails, the command waits for the other to finish before exiting.
5. It compares the images partition by partition and prints a summary: failing partitions first,
   then expected differences, with identical partitions on one line. Only the files that do not
   match are listed, with long hashes shortened, and the TUF root role to check by hand is shown
   separately; `--verbose` also lists expected differences, full hashes and an explanation of
   each check. The full JSON report is kept
   in the work directory (`--work-dir`, default `./twoliter-verify-<ami-id>`), next to
   `log.jsonl`, a detailed log of the comparison in JSON Lines. Its first line describes the AMI
   and the images compared; each following line is one step, with `time_ms`, `event` and the
   `region` it belongs to: the hashes of each region, the partition layout, every file and
   filesystem entry compared (including identical ones, with their metadata and content digests
   on both sides), the dm-verity tables, each region's result and the
   verdict. For example, `jq -c 'select(.event == "entry" and .status != "match")' log.jsonl`
   lists the entries that differ.

A rebuilt image is not byte-for-byte identical to the AMI: the build signs some artifacts with keys
generated for each build, because the release signing keys are not available to the person
rebuilding. The comparison accounts for these differences:

* The GPT, PRIVATE, BIOS-boot, DATA and data image must match byte for byte, and the B-bank,
  RESERVED and padding regions must be zero. If only one side has a data image, verification fails.
  PRIVATE holds `bootconfig.data`, whose kernel and init parameters GRUB loads at boot without
  checking a signature. Its superblocks record whether directory hashes are signed or unsigned,
  which mke2fs takes from the build host (signed on x86_64, unsigned on aarch64) in images built by
  older twoliter releases. When only that flag differs, the rebuilt PRIVATE is given the AMI's flag
  and superblock checksums, and must then match byte for byte; this is an expected difference. If
  PRIVATE differs otherwise, the report says how: which files differ, with the lines of
  `bootconfig.data` found on only one side, and whether its directory hash flag differs too.
* ROOT-A contains kernel modules signed with a key generated by the kernel build. If its bytes
  differ, both filesystems are opened and compared file by file (type, permissions, ownership,
  symlink targets, device numbers, extended attributes such as SELinux labels and file
  capabilities, and contents), ignoring the signatures appended to kernel modules.
  `/usr/share/updog/root.json`, the TUF root role updog trusts, is also expected to differ: without
  the release root role and keys, the build generates a new one. The report lists the published
  root role's sha512, expiry and key IDs; check them against the root role your repository
  publishes (for Bottlerocket, `https://cache.bottlerocket.aws/root.json`). The SBOMs,
  `/usr/share/bottlerocket/spdx-sbom.json` and `cyclonedx-sbom.json`, are expected to differ as
  long as both list the same packages by name and version: sbomtool records the time it ran,
  random document IDs and CPEs in a random order, so the rest of them is not compared. ROOT-A must
  be erofs; it is extracted with erofs-utils next to the downloaded images, unless the AMI's files
  are much larger than the rebuilt ones. Every differing file is listed in the report, and any difference other than a
  module signature, the root role or the SBOMs fails verification. Timestamps are not compared.
* BOOT-CONFIG checks the kernel command line: the AMI's `/grub/grub.cfg` in BOOT-A must match the
  rebuilt one except for the dm-verity root hash and salt, and hold a single dm-verity table for
  the same devices and parameters. Any other difference fails verification. UKI images have no
  BOOT-A; their kernel command line is the `.cmdline` section of the UKI that the firmware boots
  from EFI-A (`/EFI/BOOT/BOOTX64.EFI` or `BOOTAA64.EFI`), and it is checked the same way.
* HASH-A is formatted with a random salt, so it never matches the rebuilt one byte for byte; its
  contents are not compared. The root hash and salt the AMI boots with are the fields that
  BOOT-CONFIG allows to differ in the kernel command line.
* EFI-A and BOOT-A depend on signing keys: Secure Boot signatures, the vendor certificate in shim,
  and the GRUB public key and grub.cfg signature. If their bytes differ, they are compared file by
  file, and every difference needs one of these causes, or verification fails:
  * a signature or signing certificate (`.sig`, `.crt`, `.cer`, `.der`, `.auth`, `.esl`) that
    both images have;
  * a PE binary whose Authenticode digest matches, or that differs only in the sections holding
    embedded keys (`.vendor_cert`, `.pubkey`) and otherwise has the same headers and layout;
  * a FIPS `.hmac` file that is the HMAC of the AMI's file it names (the HMAC key is public, so
    it is recomputed rather than trusted);
  * the dm-verity root hash and salt, in `grub.cfg` or in the `.cmdline` section of the UKI,
    which BOOT-CONFIG checks.

  Files in only one image fail, which matters for UKI images: systemd-stub adds add-ons,
  credentials and extension images it finds on the EFI system partition to the boot. The kernel
  comes from the kit, so it must match apart from its signature; variants that build their own
  kernel cannot be verified, since the kernel embeds the module signing certificate generated by
  its build. A partition whose bytes differ while its files are all identical fails too, as what
  differs is not compared.

The command exits non-zero unless the verdict is `verified`.

Requirements:

* Docker, git, cargo-make and lz4.
* erofs-utils (`fsck.erofs` and `dump.erofs`). The command fails before building if they are
  missing.
* Disk space for the build plus the downloaded images; the data image is sparse but can be 20 GiB.
* AWS permissions: `ec2:DescribeImages`, `ec2:DescribeSnapshots`, `ec2:CopySnapshot`,
  `ec2:DeleteSnapshot`, `ebs:ListSnapshotBlocks`, `ebs:GetSnapshotBlock` and
  `sts:GetCallerIdentity`.

## For Maintainers

This section includes information for maintainers about testing and releasing Twoliter.

## Unit Tests and Integration Tests

If you run `cargo test` you will get the default features which includes the feature `integ-tests`.
These will be quite slow as some of them do complete builds.
If you don't have time for that, run `cargo test --no-default-features` to run only the fast tests.

## Testing the Binary in a Project

In general, if you have changes to Twoliter and want to try them out in a Twoliter project, it is as simple as building the Twoliter binary and using it in your project.
Different projects will have different ways of making sure the correct Twoliter binary is being used.
For example, Bottlerocket has a script and Makefile.toml variables that ensure the correct version of Twoliter is being used to build Bottlerocket.
The following sections describe how to use those mechanisms to use a non-released version of Twoliter.

### Testing Twoliter Changes in the Bottlerocket Repo

The process of testing changes to Twoliter in Bottlerocket is as follows:
- Commit your changes. This can be either a local commit or a commit on a git fork.
- In the Bottlerocket git repo
  - Remove the existing Twoliter binary if it exists.
  - Ensure the [nightly rust toolchain] is installed and enabled.
  - Run any/all `cargo make` commands with the following environment
    variables.

[nightly rust toolchain]: https://rust-lang.github.io/rustup/concepts/channels.html#working-with-nightly-rust

```sh
# The URL to the Twoliter git repository. This can be anything that git remote add would accept.
# Here we are using a path on the local filesystem.
TWOLITER_REPO=file:///home/myuser/repos/twoliter
# The sha of the commit you want to use. Make sure changes have been committed!
TWOLITER_VERSION=a8b30def
# These need to be set as follows.
TWOLITER_ALLOW_SOURCE_INSTALL=true
TWOLITER_ALLOW_BINARY_INSTALL=false
TWOLITER_SKIP_VERSION_CHECK=true
```

So, for example, to build a Bottlerocket image using a commit on a fork, I would look like this:

```sh
  rm -rf tools/twoliter
  cargo make -e=TWOLITER_REPO=https://github.com/webern/twoliter \
    -e=TWOLITER_VERSION=11afef09 \
    -e=TWOLITER_ALLOW_SOURCE_INSTALL=true \
    -e=TWOLITER_ALLOW_BINARY_INSTALL=false \
    -e=TWOLITER_SKIP_VERSION_CHECK=true \
  build-variant
```

### Alternative Method of Testing in the Bottlerocket Repo

Another way you can test your Twoliter changes in the Bottlerocket repo is by building twoliter and
moving it into the right place, then telling `cargo make` not to install Twoliter at all.

For example, if you have set `TWOLITER_REPO` and `BOTTLEROCKET_REPO` to the respective local git repositories, then:

```shell
cd $TWOLITER_REPO
cargo build --release --package twoliter --bin twoliter
rm -rf $BOTTLEROCKET_REPO/tools/twoliter
mkdir -p $BOTTLEROCKET_REPO/tools/twoliter
cp $TWOLITER_REPO/target/release/twoliter $BOTTLEROCKET_REPO/tools/twoliter

cd $BOTTLEROCKET_REPO

cargo make \
    -e=TWOLITER_ALLOW_SOURCE_INSTALL=false \
    -e=TWOLITER_ALLOW_BINARY_INSTALL=false \
    -e=TWOLITER_SKIP_VERSION_CHECK=true \
    build-variant
```

## Releasing

A release consists of a semver tag in the form `v0.0.0`.
We also use release-candidate tags in the form `v0.0.0-rc1`.

We use a fork of `cargo-dist` to facilitate binary releases.
The purpose of the `cargo-dist` fork is to enable cross-compilation with `cross`
We do not release Twoliter into `crates.io`.

`cargo-dist` is run by GitHub Actions, and the release workflow requires an additional approver to run the release action.

To perform a release:

- Create and merge a PR that bumps the version and changelog like [this one].
  This commit should use the desired `rc` version for the `twoliter` crate, e.g. `0.0.4-rc1`.
- Push a release-candidate tag matching the selected version, e.g. `v0.0.4-rc1`.
- That will create a GitHub Actions workflow which will create a GitHub release and attach binaries.
- An additional approver must navigate to the [Actions tab] and approve the Release workflow.
- Create a Bottlerocket PR ([example]) that uses the new version of Twoliter.
  At first, your PR will use the candidate tag.
  Before merging to the Bottlerocket repo, you will use the final release tag.
- Test Twoliter in Bottlerocket
  - `cargo make`
  - `cargo make ami`
  - `cargo make test --help`
  - More extensive testing if needed.
  - Note: If you want to use your local version of Twoliter to build Bottlerocket.
    - Delete the existing install of Twoliter if it exists.
    - Commit and push your code to your fork of Twoliter. For example: https://github.com/YOUR_GIT_ALIAS/twoliter
    - Set the following Environment variables
      - TWOLITER_REPO = Your Twoliter Repository link.
      - TWOLITER_VERSION = Hash of the commit pushed to your Twoliter repository.
      - TWOLITER_ALLOW_SOURCE_INSTALL = True, as we want to do a source install.
      - TWOLITER_ALLOW_BINARY_INSTALL = False, as we do want to use a Twoliter binary.
      - TWOLITER_SKIP_VERSION_CHECK = True, as we do not want to use a certain Twoliter binary version.
  - For example,
```
  rm -rf tools/twoliter
  cargo make -e=TWOLITER_REPO=https://github.com/YOUR_GIT_ALIAS/twoliter \
    -e=TWOLITER_VERSION=HASH_OF_COMMIT \
    -e=TWOLITER_ALLOW_SOURCE_INSTALL=true \
    -e=TWOLITER_ALLOW_BINARY_INSTALL=false \
    -e=TWOLITER_SKIP_VERSION_CHECK=true
```
- When it's working, create a new PR to the Twoliter repo dropping the `-rc` in the version string.
- Merge the Twoliter PR and push a finalized tag, e.g. `v0.0.4`.
- An additional approver must navigate to the [Actions tab] and approve the Release workflow.
- Once the GitHub Actions workflow finishes, update the Bottlerocket PR to your finalized tag.
- Merge the Bottlerocket PR
