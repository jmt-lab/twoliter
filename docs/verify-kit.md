# Verifying a kit

`twoliter verify kit bottlerocket-core-kit 17.3.0` checks that a published kit can be reproduced
from source:

1. It reads the kit image index `<registry>/<kit>:v<version>`, where `--registry` defaults to
   `public.ecr.aws/bottlerocket`, and downloads the image of each architecture to verify
   (`--arch`, repeatable; defaults to every architecture the kit is published for). The kit
   metadata in the image config names the kit to build and must have the requested version.
2. It clones the source (`--repo`, default `https://github.com/bottlerocket-os/<kit>`, or an
   existing clean clone via `--source-dir`) and checks out the commit tagged `v<version>`, or the
   one given with `--commit`. Its release version must be the kit's version.
3. Kit builds set the image creation time to the time of the commit they build, so the command
   fails before building if the published kit was not created at the commit's time: it was built
   from a different commit, and passing the right one with `--commit` is needed. Kits pinning a
   twoliter older than 0.26.0 used the build time, so for them this is only a warning.
4. It runs `make build KIT=<kit> ARCH=<arch>` in the checkout for each architecture, so the kit
   is rebuilt with the twoliter version pinned in its Makefile. Kits pinning a twoliter older
   than 0.26.0 are not expected to reproduce. The build output is written to `build-<arch>.log`
   in the work directory, and its last lines are shown if the build fails; `--verbose` shows it as
   it runs instead.

   The build runs in the SDK image of the architecture given with `--sdk-arch`, rather than of
   the host, which builds would use by default. The SDK image of each architecture holds its own
   build of the cross toolchains, and they produce different code, so the rebuild has to use
   the SDK of the architecture the published kit was built on. Bottlerocket kits are built on
   x86_64 for both target architectures: the published aarch64 `bottlerocket-core-kit` 17.3.0
   ships the Rust standard library of the amd64 SDK image (`libstd-df706d80e0c7c39a.so`; the
   arm64 image has `libstd-54f54d71a32e0cb6.so`). So `--sdk-arch` defaults to x86_64. The
   command checks the SDK's image index against the digest in `Twoliter.lock`, pulls the image
   it lists for that architecture, tags it with the name the build uses and sets
   `DOCKER_DEFAULT_PLATFORM` for the build. Once the build ends, the name points at the image
   Docker had under it before again. On a host of another architecture, the SDK runs under
   QEMU user-mode emulation, which must be registered with binfmt_misc (for example with
   `docker run --privileged --rm tonistiigi/binfmt --install amd64`), and the build is several
   times slower.
5. It compares each rebuilt image against the published one. An architecture is verified when
   its rebuilt manifest digest equals the published one, which makes the config and every layer
   identical. Otherwise the summary lists what differs, as rebuilt vs published: config fields,
   with the kit metadata label decoded; layers, matched by the package directory or `repodata`
   they hold; and within a differing layer, each file whose type, contents, mode, ownership,
   modification time or link target differs. The full JSON report is kept in the work directory
   (`--work-dir`, default `./twoliter-verify-<kit>-v<version>`).
6. Each package whose bytes differ is compared by header and payload with `reprosys compare-rpm`,
   so the cause is shown without unpacking it by hand:
   * Header tags are compared one by one, except those derived from the payload: file digests
     and sizes, the installed size, and the payload digests and sizes. Tags holding a value per
     file show the file. The signature header holds only digests of the header and payload, and
     is not compared. Each package's file digests and sizes are checked against its own payload.
   * Payload files are compared by type, contents, mode, link target and device number, as for
     ROOT-A in [`verify ami`](../README.md#verifying-an-ami); ownership and timestamps are
     compared in the header.
   * Kernels sign their modules with a key generated by each kernel build, so a kernel module
     that differs only in its appended signature is an expected difference (`note`). The kernel
     image (`/boot/vmlinuz`) and signing certificate (`certs/signing_key.x509`) embed that key's
     certificate, so a difference in them is a warning (`warn`) rather than a failure.
   * Go 1.25 to 1.27 give cgo packages compiled with link-time optimization a random action ID
     on every build ([golang/go#81040](https://github.com/golang/go/issues/81040), fixed in
     Go 1.28). The Bottlerocket SDK's `CGO_CFLAGS` enable LTO, so the build IDs of Go binaries
     using cgo differ even though their code is identical. A Go binary is an expected difference
     (`note`) when its Go build ID differs and every byte outside its Go and GNU build ID notes
     is identical. The build IDs only identify a build; nothing reads them at run time.
   * A package differing only in expected ways or warnings is an expected difference only when
     nothing else differs. `repodata`, which records every package's checksum, is an expected
     difference only when some package differs and only in expected ways; its files may differ in
     contents, and those named by their checksum may be renamed, but nothing else. Any other
     difference, including one in a header tag, fails verification.

   Kits without kernels, such as `bottlerocket-core-kit`, are expected to reproduce byte for
   byte, apart from the build IDs of Go binaries using cgo. For `bottlerocket-kernel-kit`, the
   verdict matches `verify ami`'s: verified except for signing-dependent content. `--verbose`
   lists expected differences, which are otherwise counted.

The command exits non-zero unless every architecture verifies. Requirements: Docker, git, make,
and disk space for the build plus the downloaded kit images.
